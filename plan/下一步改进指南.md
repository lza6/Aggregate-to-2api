# 听风AI · 下一步改进指南

> **适用版本基线**：v4.2/v5.0（`api/main.py=4.2.0` · `pyproject.toml=5.0.0` · `docker-compose=v4.2.1`）
> **生成日期**：2026-08-27 · **性质**：纯改进/迭代指南（不涉及改码，供后续 AI 据此落地）
> **前置**：先读 `README.md`、`workflow_status.md`、`report.md`、`api/main.py`、`frontend/src/api.ts`

## 0. 文档目的与总原则

本项目已从 0-1 做到生产可用的 v4 网关（高并发生图 + TryingOpen 文本/Agent 网关 + React 管理面板）。
本指南的目标是 **1→2 的量级跃升**：不重构没坏的东西、不造已有轮子，只在现有实现上做**精准的迭代升级**。
每类改进给出：**问题证据 → 目标 → 落地步骤 → 验收标准 → 风险**，方便后续 AI 直接照做。

> ⚠️ 所有改动遵循仓库既定约束：
> 1. 改 `api/` 后必须 `python scripts/sync_deploy.py sync` 同步 `deploy/api/`
> 2. 前后端契约以 `frontend/src/api.ts` 为唯一真相源
> 3. 配置项在 `api/config/`，`.env.example` 需同步
> 4. 版本号在 `api/main.py` 与 `README.md` 两处维护（**但当前已失同步，见 P0-1**）
> 5. 禁止删除/覆盖真实数据；涉及数据库迁移需先确认

**验收**：`grep -rn "v4\|5.0" 上述文件` 输出一致；`sync_deploy.py check` 通过。
**风险**：低（纯文案/元数据，无逻辑变更）。

### P0-2 前端 E2E 冒烟无法运行（缺依赖）

**证据（已验证）**：`node frontend/e2e-smoke.cjs` → `Cannot find module 'playwright-core'`；`frontend/package.json` 的 dependencies/devDependencies 均未声明 `playwright` / `playwright-core`。
**目标**：让 `e2e-smoke.cjs` 可复跑，作为前端真实路径的快速回归门禁。
**落地步骤**：
1. `cd frontend && npm i -D playwright-core`（或 `playwright`，按脚本实际 import 决定）。
2. 确认脚本能定位到本机 Chromium（`findChromium` 逻辑可能需指到系统 Chrome/Edge）。
3. 在 `package.json` 加 `"smoke": "node e2e-smoke.cjs"` 脚本。

**验收**：`npm run smoke` 启动 dev/preview 后真实打开 `/admin` 并断言关键元素无异常退出。
**风险**：低；若脚本依赖正在运行的 8100 服务，需在脚本内自起 preview。

### P0-3 一键启动脚本找不到 cf_solver（静默跳过，端口依赖断裂）

**证据（已验证）**：`start.ps1` 只探测 `cf_solver` / `..\cf_solver` / `..\GPT自动化注册的项目\cf_solver` 三个路径，而真实存在的是 **`deploy/cf_solver`** → 一键启动会打印「未找到，跳过」，随后 API 因无 solver 而 turnstile 全失败。
**目标**：一键启动真正可用。
**落地步骤**：
1. 在 `start.ps1` 的候选路径中加入 `deploy\cf_solver`。
2. 启动前校验 `deploy/cf_solver/boterdrop_wrapper.py` 存在；缺失时给出明确提示而非静默跳过。
3. （可选）README 快速启动章节补充「cf_solver 现位于 `deploy/cf_solver`」。

**验收**：在干净环境运行 `start.bat`，日志出现 `[cf_solver] 就绪` 且 8001 端口可连。
**风险**：低。

### P0-4 测试基线有 9 个真实失败 + 3 个 benchmark ERROR（回归门禁失灵）

**证据（已验证，逐条根因）**：
| 测试 | 失败根因 |
|------|---------|
| `test_priority_queue.py` ×9 | 测试桩 `_DBStub.create_request` 未带 `client_ip` 参数，而 `engine.py:202` 已按新契约传入 `client_ip=` → 桩过期，**测试没跟上 v4.4.3 的 client_ip 透传改动** |
| `test_worker_auto_scale.py::test_resume_from_queue_without_db_returns_zero` | `_resume_from_queue()` 已是 `async def`，测试漏 `await`，断言 coroutine==0 恒假 |
| `test_telemetry.py` ×3 | 测试用 `os.environ["IF_OTEL_ENABLED"]="1"` 直接改环境，但 `api/config` 模块在 import 时已用 `os.environ.setdefault` 固化默认值 → **污染顺序依赖**（与已知记忆 `pytest-pollution` 一致） |
| `test_providers.py::test_imagefree_provider_needsengine` | 孤立运行**通过**，仅在全量时因其他顺序副作用失败（需进一步定位共享全局单例污染） |
| `test_benchmark.py` ×3 | ERROR（非 fail）——pytest-benchmark 缺失或 fixture 装配问题 |

**目标**：全量 `pytest tests/ -q` 恢复全绿，让回归门禁可信。
**落地步骤**：
1. **优先修 `test_priority_queue.py`**（9 个，P0）：把 `_DBStub.create_request` 签名补上 `client_ip=None`（或按 `engine.py` 实际调用签名对齐）。这是最直接、影响最广的一个。
2. `test_worker_auto_scale.py:254`：`assert await engine._resume_from_queue() == 0`。
3. `test_telemetry.py`：改用 `monkeypatch.setenv` 且**在 import `api.telemetry` 之前**设置，或用 `api.config` 提供的 reload/reset 钩子；参照 `tests/conftest.py` 的既有隔离模式。
4. `test_benchmark.py`：确认 `pytest-benchmark` 是否在 `requirements.txt`；若 benchmark 非 CI 必需，建议在 `pyproject.toml` 用 marker 隔离（如 `-m "not benchmark"`）并在 CI 排除。
5. 逐个跑 `test_providers.py` 全文件确认顺序污染根因（疑似 `api.worker.Engine` 全局单例或 `registry` 单例被前序测试改状态）。
6. 修完后全量跑一次确认 0 fail。

**验收**：`pytest tests/ -q --disable-warnings` 输出 `X passed`，0 failed 0 error（benchmark 若隔离则注明）。
**风险**：中。改测试文件不影响生产代码；但要**改测试而非改生产去迁就测试**——若 `engine.py` 的新 `client_ip` 契约是正确设计（v4.4.3 确有此意），则只补桩。

> ⚠️ **环境风险（已观测）**：机器上存在 4 个早于本会话启动的遗留 `python -m pytest tests/` 进程（系统 Python311，8/25、8/26 启动），疑似长期持有 `data/` 下 SQLite 锁，会拖慢/阻塞后续全量测试。修复 P0-4 前建议先由用户确认后清理这些僵尸进程，避免「改对了却因锁跑不过」的假象。

## 4. P3 —— 产品化与体验增强（功能层，量大但非阻塞）

> 以下为**迭代方向建议**，按业务价值排序，落地前请先 `git log` 确认没有已存在的轮子。

### P3-1 生图主链路「同步/异步」一致性补强
- **现状**：`/v1/generate`（同步）与 `/v1/generate/async` 各自实现，同步会阻塞到出图。
- **建议**：同步端点内部复用异步 task + 短轮询/SSE 等待，保证两者语义一致、超时/取消路径统一。**先读 `dispatch.py` 现有实现再动手，避免重复造轮子。**

### P3-2 画廊与资源 GC 的可观测闭环
- **现状**：`api/base64_store.py`（base64 冷热分离）、`api/img_gc.py` 已有清理逻辑，`test_img_gc.py` 覆盖。
- **建议**：在 `/v1/stats` 暴露「当前 base64 冷/热占比、待清理文件数、预计释放空间」，让资源水位可观测。属纯增量。

### P3-3 ChatPlayground 体验打磨（前端）
- 会话持久化已做（`localStorage`）。建议补：**导出完整会话为 JSON**（当前已支持 Markdown）、**模型按「生图/对话/工具/多模态」分组下拉**、**思考链折叠默认收起**。均有后端字段支撑，纯前端。
- 加 **Token/成本估算**：`/v1/chat/usage` 已有数据，可在对话面板显示「本次预估 Token + 当前剩余额度」实时提示，提升小白友好度。

### P3-4 管理面板：号池/代理池健康度一键体检
- **现状**：`/v1/diagnostics` 是只读体检，`/v1/account-pool`、`/v1/proxy-pool` 分别展示。
- **建议**：新增一个「健康体检」页签，聚合 diagnostics + 两个池的空闲/冷却/当日配额，用 `ProviderCard`/`StatCard` 复用渲染，给出「可立即出图能力」综合分。

### P3-5 可访问性（a11y）基线
- **现状**：未做专门 a11y 审计。
- **建议**：用 axe 跑一次 `/admin`，先修 CRITICAL/HIGH（对比度、表单 label、键盘可达），达标后再谈新增。符合 `web/testing.md` 与 `a11y` 规则。

### P3-6 性能：前端包体积
- **证据**：`npm run build` 产物中 `vendor-chart-*.js` gzip 105KB（recharts），`index` gzip 68KB。`web/performance.md` 预算 app 页 <300KB 仍达标，但 recharts 可考虑按需/懒加载以进一步压。
- **建议**：确认 Dashboard 图表懒加载；`BarChart` 是否可换更轻的实现或分包。属可选优化。

  C1. P2-1 前端测试骨架                        → npm test 过
  C2. P2-2 CI 分档 + markers 修复
