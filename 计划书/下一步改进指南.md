## 一、项目现状全景与第一性原理深度剖析

### 1.1 什么是本质？(First Principles Decomposition)

听风AI (Imagefree-2API) 的本质是一个**基于高并发异步逆向网关的 AI 图像生成算力聚合系统**。
其核心价值闭环为：
1. **上游**：通过自动化逆向机制，将多家免费或低成本的上游 AI 图像生成服务（imagefree.net, aifreeforever.com, nanobanana-pro.com 等）抽象为标准化算力单元；
2. **中台**：通过多级代理池、动态号池、验证码破解求解器（CF Turnstile Solver）、自适应路由算法及内存优先队列，抹平上游的风控、限流、不稳定与时延波动；
3. **下游**：向客户端（用户、开发者、Web 界面、三方应用）提供完全兼容 OpenAI 规范的统一 API (`/v1/chat/completions`, `/v1/images/generations`, `/v1/tasks/{id}`)。


## 三、核心模块突破与极致优化方案

### 3.1 逆向破解与验证码求解自治 (CF Turnstile 突破)

#### 第一性原理
Turnstile 的本质是 Cloudflare 收集浏览器 WebGL、Canvas、AudioContext、Navigator、TLS JA3、IP 纯净度等指纹后生成的短效验证凭证。
**瓶颈根因**：单实例 Playwright 开销过大，容易引起内存挤压与 429 排队。

#### 升级方案 (v5.0): `SolverGuard Cluster + CDP 反检测引擎`
1. **分布式求解节点池 (Solver Node Federation)**：
   - 将 `cf_solver` 从单机 8001 端口扩展为支持多节点负载均衡（支持本地 Chrome、远程 VPS 节点、无头 Docker 节点动态接入）。
   - 引入健康检查与动态加权轮询（Weighted Round-Robin with Health Checks），一个节点 429 自动熔断 60s 并平滑切换备用节点。
2. **CDP (Chrome DevTools Protocol) 极速模式**：
   - 抛弃重量级页面渲染，拦截非必要静态资源（CSS, Font, Image, Media），仅保留 CF 脚本执行上下文，求解时间由 6-8s 压缩至 1.8-2.5s。
3. **Turnstile Token 预热与双缓冲池 (Token Double-Buffering)**：
   - 维护一个容量为 $N$ (默认 10~20) 的热 Token 队列，后台守护协程根据消耗速率自适应求解，请求到达时 **0 毫秒** 获取有效 Token。

```python
# 伪代码：Token 预取双缓冲调度设计 (Token Double-Buffer)
class TurnstilePrewarmPool:
    def __init__(self, target_capacity=15, ttl=110):
        self._queue = asyncio.Queue(maxsize=target_capacity * 2)
        self._target_capacity = target_capacity
        self._ttl = ttl # Turnstile token 有效期通常为 120s

    async def get_token(self) -> str:
        while True:
            token_obj = await self._queue.get()
            if time.time() - token_obj.created_at < self._ttl:
                return token_obj.token
            # 过期自动丢弃，重新获取

    async def _prewarm_loop(self):
        while True:
            if self._queue.qsize() < self._target_capacity:
                token = await solver_cluster.solve_turnstile()
                await self._queue.put(TokenItem(token, time.time()))
            await asyncio.sleep(0.5)
```

### 3.2 智能号池全自动化生命周期管理 (Account Pool 2.0)

#### 痛点与破局
当前生产号池依赖单源邮箱与单点脚本，速率受阻。

#### 升级方案 (v5.0): `多源弹性邮箱抽象 + 账号自动再生循环 (Auto-Regen Cycle)`
1. **多邮箱提供商适配器 (Mail Provider Strategy)**：
   - 统一接口 `BaseMailSource`，实现：
     - `LinshiMailSource` (自建/现有临时邮箱)
     - `MailTmSource` (mail.tm REST API，速度快且稳定)
     - `GuerrillaMailSource` (支持免认证拉取)
     - `CustomImapSource` (自建域名邮箱通配符捕捉，彻底消除 429 限制)
2. **账号健康状态机与自动延寿 (Account FSM)**：
   ```
   [未注册] ──► [注册中] ──► [就绪 (Active)] ──► [工作负载中] ──► [每日限额 (Cooling)]
                                   │                                     │
                                   ▼ (401/403)                           ▼ (次日 00:00)
                              [失效 (Dead)] ◄─── (重试失败) ────── [重新激活/签到]
   ```
3. **断点续跑与故障自动隔离**：
   - 注册任务由独立的自适应 Worker 驱动，失败自动分类退避（CF阻断退避 30s，邮箱频控退避 60s，IP污染退避 120s），杜绝无效空转。

### 3.3 代理网络智能分层与健康度评分 (Proxy Pool Pro)

#### 升级方案 (v5.0): `动态加权健康评分机制 (Dynamic Health Scoring)`

引入基于滑动窗口的代理评分模型：
$$Score = \left( \frac{S_{recent}}{N_{recent}} \times 0.6 + \frac{1}{\log_{10}(Latency_{ms} + 10)} \times 0.4 \right) \times Penalty_{cooldown}$$

1. **分级代理路由策略**：
   - **Tier 1 (Residential / Kookeey)**：专供注册、风控突破与高优先级任务。
   - **Tier 2 (Free Verified Proxy)**：专供常规生成与状态轮询。
   - **Tier 3 (Direct / Local IP)**：仅当无阻断时参与低风险操作。
2. **毫秒级主动剔除与自愈**：
   - 代理连续 2 次触发 403/Cloudflare Block，立即冻结 300 秒，降级评分；当检测到连续 3 次探测成功，平滑恢复权重。

### 3.4 多提供商智能自适应路由引擎 (Adaptive MAB-EWMA 3.0)

#### 算法升级
现有 MAB-EWMA 基础上，加入**时延方差衰减**与**动态探索比例**：

$$Reward_i = \frac{SuccessRate_i}{\log_{2}(P90\_Latency_i + 1)} \times \left(1 - \frac{CurrentLoad_i}{MaxCapacity_i}\right)$$

1. **多维度自适应探索-利用 ($\epsilon$-Greedy with Decay)**：
   - 默认利用率 90%，探索率 10%。
   - 当主提供商出现连续熔断时，探索率动态放大至 40%，实现秒级流量迁徙。
2. **提供商功能矩阵感知 (Capabilities Matrix)**：
   - 自动识别请求特征（如：是否含参考图、分辨率要求、提示词长度、特定模型参数），直接命中具备最佳匹配能力的 Provider，无需盲目试错。

### 3.5 队列调度、并发控制与图生图分布式锁

#### 1. 内存有界优先级队列优化
- 升级双层桶队列：`Admin/VIP (Priority 0)` > `Normal (Priority 1)` > `Batch (Priority 2)`。
- 任务入队瞬时原子落盘并广播 SSE 事件，保证即使在突发 500 RPS 冲击下，主事件循环延时不超过 2ms。

#### 2. 图生图互斥锁演进 (无锁化与基于租约的分布式锁)
- **现状**：PID 文件锁易受容器环境干扰。
- **演进**：
  - 基于 SQLite 内部行级原子事务的排他租约锁 (`Lease Lock`)，替代文件系统 PID 锁。
  - 具备 **自动超时续租 (TTL Heartbeat)** 与 **异常宕机自动释放** 特性，彻底杜绝僵尸死锁。

### 3.6 数据库、连接池与多级缓存极致优化 (Storage & Cache)

1. **SQLite 极限性能调优参数清单**：
   - `PRAGMA journal_mode = WAL;` (写入与读取完全无锁并发)
   - `PRAGMA synchronous = NORMAL;` (兼顾断电安全与极致 IOPS)
   - `PRAGMA cache_size = -64000;` (开启 64MB 内存缓存页)
   - `PRAGMA mmap_size = 268435456;` (启用 256MB 内存映射 I/O)
   - `PRAGMA busy_timeout = 5000;` (5秒内自动重试，消除 Database Locked 报错)
2. **多级冷热分层存储**：
   - 任务元数据存入 SQLite。
   - Base64 / 最终生成的大图二进制数据自动写入独立目录缓存或对象存储，DB 中仅存储哈希索引与相对路径，保持 DB 文件精简。
