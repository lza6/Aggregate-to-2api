## 2. 当前项目基线

### 2.1 项目目标与用户

听风AI 是「上游免费 AI 能力的聚合与再分发网关」：把 N 家上游的「人机验证（Turnstile）+ 账号额度 + IP 风控 + 异步生成」四重摩擦，压缩成开发者侧的一个 `POST /v1/generate` / `POST /v1/chat/completions` 同步调用。

**一句话本质**：核心价值 = 四重摩擦的消除效率。护城河与瓶颈完全一致，都在「四重摩擦消除」上。

**目标用户**：开发者（调 OpenAI 风格 API）+ 站长（管理面板运营号池/代理池/Provider）。公益开放，生图/聊天不限 Key。

### 2.4 主要入口与运行路径

- **应用入口**：`api/main.py:107` `app = FastAPI(version="8.2.3", lifespan=lifespan)`
- **核心数据流**：调用方 → `POST /v1/generate` → `routes/generate.py` → `dispatch.py` → `PriorityQueue` → `worker/engine.py` → `providers/<provider>.py` → 上游；SSE/WS 反向推送状态。
- **聊天链路**：`POST /v1/chat/completions` → `routes/chat.py`(654) → `providers/tryingopen/` → 上游 tryingopen.com（13+ 开源大模型，匿名 + 代理池轮换）。
- **启动**：`python deploy/cf_solver/boterdrop_wrapper.py`（8001）+ `uvicorn api.main:app --port 8100`，或 `start.ps1` / `start.bat` 一键拉起。

`docs/architecture-evolution.md` 结论性指出，以下在触发器出现前**都是负优化，本指南不纳入**：

- 换 Postgres（数据 17k 行不到百万，SQLite 单文件轻松扛 10 年）

- 分库分表（伪需求）

### 5.1 P0-S1：storage/ Redis 适配器热路径真接线（半成品收尾，最高优先）

**当前状态**：半成品。`api/lifespan.py:66-90` 已在 startup 装配 `RedisStorageAdapter`（`IF_STORAGE_BACKEND=redis` 且 `IF_REDIS_URL` 非空时），但 `api/request_guard.py` 的限流/令牌桶热路径**未真正消费**该适配器。

**证据**：
- `api/request_guard.py:46` `_storage_adapter = None`
- `api/request_guard.py:52-63` 只有 `set_storage_adapter()` / `get_storage_adapter()` 装配函数

- `api/request_guard.py:114` `_l1_token_buckets: dict[str, list[float]]`（纯内存）
- `api/request_guard.py:208-209` 令牌桶 `bucket = _l1_token_buckets.setdefault(key, [capacity, now])`（纯内存）
- **全文件无 `acquire_token` / `_storage_adapter.acquire` / `sliding_window` 对适配器的调用**

**根本原因**：v8.0 P1-1 只完成了「装配层」（lifespan 注入 + set/get 函数 + 测试兜底 `tests/test_redis_adapter.py`），但「消费层」（request_guard 热路径分叉走 Redis）未落地。这导致 `IF_STORAGE_BACKEND=redis` 时空有适配器单例，限流仍走内存 —— 双实例部署时集中式限流**名存实亡**。

**影响**：
- 双实例部署时 per-IP 限流不共享 → 集中式限流失效
- 任何相信「P1-1 已完成」而跳过验证的执行方会埋下生产隐患
- `tests/test_request_guard_redis_mode.py`（旧指南声称新建）需确认是否真存在且断言了热路径

**推荐方案**（L2 中风险，应隔离实施）：
1. `request_guard._ip_lock(ip)` 分叉：内存模式走现有 `threading.Lock` 分片；Redis 模式调 `_storage_adapter.acquire_token(ip, ...)`（RedisStorageAdapter 已有 SET NX EX + ZSET Lua 滑窗，见 `api/storage/redis_adapter.py`）。
2. `_l1_token_buckets` 令牌桶同理：Redis 模式走适配器的 token bucket（Redis INCRBY + EXPIRE）。
3. Redis 不可用时降级到内存（已有 `set_storage_adapter(None)` 回退路径，lifespan:88）。
4. 单机模式（`IF_STORAGE_BACKEND=sqlite`，缺省）零回归。

## 12. 根本原因分析（P0/P1 关键项）

### 12.1 P0-S1 storage 半成品

- **表面现象**：`IF_STORAGE_BACKEND=redis` 时空有适配器单例，限流仍走内存。
- **直接原因**：`request_guard.py` 只加了 `set_storage_adapter()`/`get_storage_adapter()` 装配函数，热路径 `_ip_lock`/`_l1_token_buckets` 未分叉调适配器。
- **系统性原因**：v8.0 P1-1 拆成「装配层」与「消费层」两步，只完成了装配层（lifespan 注入 + 测试兜底），消费层因「单机缺省零回归」的保守策略被推迟，但未在指南中标注为半成品，导致旧指南误称已完成。
- **影响半径**：双实例部署集中式限流失效；任何相信「P1-1 已完成」的执行方埋下生产隐患。
- **相关文件**：`api/request_guard.py:46-63,66-72,114,208-209`、`api/lifespan.py:66-90`、`api/storage/redis_adapter.py`、`api/storage/factory.py`
- **当前证据**：`rg _storage_adapter api/request_guard.py` 仅装配函数，无热路径调用。
- **尚未确认的假设**：`tests/test_request_guard_redis_mode.py` 是否已存在并断言热路径 —— 执行方落地前先确认。
- **最小验证方法**：`rg "acquire_token|_storage_adapter\." api/request_guard.py`，若仅返回装配函数则确认半成品。

### 12.2 P1-A1 agent 真闭环

- **表面现象**：`api/agent/` 子系统已落地，是否真调 LLM **已确认（静态）**——非存疑。
- **直接原因**：未补 E2E 验收关卡，非未调 LLM。源码静态确认 `intent.py:107-148`/`critic.py:107-138`/`memory.py:267-289` 均有 `provider.chat_collect` 真实 LLM 调用路径（走 tryingopen 免费上游，`IF_MOCK_UPSTREAM=0` 默认真实，`=1` 才走 Mock 兜底）。
- **系统性原因**：agent 化批次获用户真实付费授权后，「装配真实 LLM 调用」已完成，但「端到端验收 + 生产可观测」缺关卡——E2E 测试（`tests/integration/test_agent_e2e.py`）未补、Prometheus 指标未加。
- **影响半径**：真实 LLM 路径已存在不会伪闭环；但缺 E2E 则无法证明 `intent→memory→consolidation` 端到端真绿，生产异常无指标可观测。
- **当前证据**：`rg "provider.chat_collect|chat_provider.chat_collect" api/agent/*.py` 命中 intent.py:122 / critic.py:138 / memory.py:289（真实调用点已确认，非 Mock 悬空）。
- **尚未确认的假设**：默认 `IF_MOCK_UPSTREAM=0` 走真实 tryingopen 上游时，生产是否有可观测指标/日志 —— 执行方落地时补 E2E + 指标后确认。
- **最小验证方法**：`rg "provider.chat_collect|chat_provider.chat_collect" api/agent/*.py` 确认调用点（已过）+ 补 `tests/integration/test_agent_e2e.py` 跑绿。

### 12.3 P2-F1 CI flaky

- **表面现象**：`test_account_growth::test_account_pool_growth_field` CI 1/37 404。
- **直接原因**：合理推断 —— CI 上号池自动注册与断言时序竞争。
- **系统性原因**：后台注册 worker 异步写库，测试断言未等待最终一致性。
- **最小验证方法**：本地 `pytest tests/test_account_growth.py -v` 3 轮 + CI 连续 3 次 push。
