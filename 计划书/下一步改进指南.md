## 2. 当前项目基线

### 2.1 项目目标与用户

听风AI 是「上游免费 AI 能力的聚合与再分发网关」：把 N 家上游的「人机验证（Turnstile）+ 账号额度 + IP 风控 + 异步生成」四重摩擦，压缩成开发者侧的一个 `POST /v1/generate` / `POST /v1/chat/completions` 同步调用。

**一句话本质**：核心价值 = 四重摩擦的消除效率。护城河与瓶颈完全一致，都在「四重摩擦消除」上。v9.0.0 的跃迁方向 = 把"单步调用"升级为"多步智能体编排"，把摩擦消除从"单点"升级到"链路"。

**目标用户**：开发者（调 OpenAI 风格 API）+ 站长（管理面板运营号池/代理池/Provider）。公益开放，生图/聊天不限 Key。

### 2.4 主要入口与运行路径

- **应用入口**：`api/main.py` `app = FastAPI(version="8.6.5", lifespan=lifespan)`
- **生图核心数据流**：调用方 → `POST /v1/generate` → `routes/generate.py` guard+prepare → SQLite 入库 → `dispatch.py` → `PriorityQueue` → `worker/engine.py`（worker 池 4-16 自适应 + scaler 多维评分）→ `providers/<provider>.py` → 上游；SSE/WS 反向推送状态。
- **聊天链路**：`POST /v1/chat/completions` → `routes/chat.py` → `providers/tryingopen/` → 上游 tryingopen.com（13+ 开源大模型，匿名 + 代理池轮换）。
- **agent 链路**：`POST /v1/agent/intent` → `agent/intent.py:_llm_classify` → `registry.all_chat_models()` → `provider.chat_collect` 走 tryingopen 免费上游（`IF_MOCK_UPSTREAM=0` 默认真实）→ 返回 IntentResult；`agent/memory.py` 记忆巩固 worker（lifespan 启动）做 L0-L3 巩固。
- **启动**：`python deploy/cf_solver/boterdrop_wrapper.py`（8001）+ `uvicorn api.main:app --port 8100`，或 `start.ps1` / `start.bat` 一键拉起。

### 2.7 已知限制（触发器未出现前的负优化）

`docs/architecture-evolution.md` 结论性指出，以下在触发器出现前**都是负优化，本指南不纳入**：

- 换 Postgres（数据 <百万行，SQLite 单文件轻松扛 10 年；sqlite-vec 向量索引也已就绪）
- 上 Kafka（最小集群 >2GB 内存，比 api 本身还重；已有 asyncio.PriorityQueue + 持久化队列开关）
- 分库分表（伪需求）
- Load Balancer（单实例部署，Nginx/HAProxy 只在 ≥2 实例时有意义；但 cf_solver 多节点联邦属真实瓶颈，见 §8.1）
- 引入 Redis 为强依赖（保持 `IF_STORAGE_BACKEND=sqlite` 缺省零依赖，Redis 仅可选集中式限流）

## 19. 根本原因分析（关键项）

### 19.1 旧指南基线漂移（系统性根因）

- **表面现象**：旧版《下一步改进指南.md》基线停留在 v8.2.3，列了 136h 待办，但代码已是 v8.5.0。
- **直接原因**：旧指南写于 v8.2.3，未随 v8.3.0/v8.5.0 发版同步更新。
- **系统性原因**：发版节奏快（v8.0→v8.5.0 跨 5 个版本），但指南更新未纳入发版 SOP（`docs/SOP.md` 无"指南同步"步骤）。
- **影响半径**：执行方误用旧版会把已落地项当待办重做（storage 热路径/大文件/agent E2E/litestream/Grafana/向量/成本预测/flaky 根治）。
- **修复**：本版全面重写并覆盖旧版 + N1 把"指南同步"纳入发版 SOP。

### 19.2 DAG 跃迁的复用风险

- **表面现象**：G4 DAG 需复用 agent/vector/SSE/queue 四套子系统。
- **直接原因**：DAG 是"串联层"，不是"新建层"——它调用现有子系统而非重写。
- **系统性原因**：执行方若不遵循"只追加不重构"铁律，可能破坏现有 agent 模块。
- **影响半径**：破坏 intent/critic/memory 会导致 v8.5.0 已落地的 agent E2E 回归。
- **修复**：§6.1 明确禁区"不得改现有 agent 模块"+ AST 契约 `test_async_sync_contamination.py` 必跑 + TDD 先测后写。

### 19.3 运行时验证缺口的系统性

- **表面现象**：本指南所有"已落地"结论来自静态确认，非运行测试。
- **直接原因**：本次授权边界为"只产文档，不跑不装"。
- **系统性原因**：规划阶段无法跑测试（环境/权限约束），执行阶段才跑。
- **影响半径**：静态确认的"已落地"可能存在运行时回归未发现。
- **修复**：执行方落地前必先跑 `pytest -m "not integration and not chaos and not slow"` 建立回归基线 + 关键模块 mypy strict + ruff + 前端 vitest/build 全绿，再动手。

### 32.4 R3 副作用评估（Reflexion 反馈修正）

> 本节回应 Reflexion 审计"R3 修复建议未评估对 ip_blocklist_store 独立性设计副作用"的反馈。

**原建议（v8.6.1 首版 §32.2 R3）**："让 ip_blocklist_store 复用 DB 连接池" → **已废弃**。

**副作用分析**：ip_blocklist_store 当前用**独立 aiosqlite 连接**（`api/db/ip_blocklist_store.py:34` `_get_conn` 每次新建连接，非共享 DB 连接池），这是有设计理由的——封禁表独立于主库（`data/imagefree.db`），避免主库写压力（0.2s 批量写 + worker 高频 mark_finished）影响封禁判定的响应延迟。若合并进 DB 池，封禁查询会与主库写排队，限流/封禁的 per-IP 响应可能从微秒级退化到毫秒级。

**修正方案**（v8.6.1 Reflexion 轮采纳）：**不动独立连接设计**，改在 store 内部加 `asyncio.Lock` 串行化写操作（`add_or_update`/`remove`/`cleanup`），并把 `busy_timeout` 从 10s 提升到 30s，让并发写排队等待而非报 `database is locked`。读操作（`is_blocked`/`get_rule`）不受锁影响（WAL 多读并发）。

**验收**：5 轮全量单测 `test_openapi_contract::TestSecurityResponseContract::test_block_ip_record_fields` 0 失败 + ip_blocklist 独立连接保持（`grep "_get_conn\|aiosqlite.connect" api/db/ip_blocklist_store.py` 仍为独立连接）。
