# Feature Specification: 008 生产化终局审计与主动补强（Production Hardening）

## Problem Statement

听风AI（imagefree-2ai）已上线生产（20.204.27.154，v20.2.0），但**以"单机可跑"标准交付**，
未按"抗高并发、顶级安全、可维护、可交接、可增长"的成熟 SaaS 标准全面审查。本 spec 做终局审计：
不限于前后端衔接，覆盖功能完整性、契约一致性、极限压测、SQL 安全、可观测性、文档/SOP/ADR、
目录治理、产品增长与验证记录防重跑，直至形成真实可交付闭环。

## 背景事实（已核验，2026-09-26）

- 部署：20.204.27.154（ARM64）nginx 443 → imagefree-api 8100 + cfsolver 8001（camoufox ~3s/token，单 page）
- 代理池：IF_FREE_PROXY=1 已启用，2076 可用；imagefree 单 IP 忙 → 代理换出口（v20.2 修复，并发 4/4）
- 聊天：tryingopen 真实路径（IF_MOCK_UPSTREAM=0），Anthropic/SSE/agent plan 均 200
- 版本：v20.2.0 全链一致；Releases v20.0.0/v20.1.0/v20.2.0 已发
- Spec 007：phase=plan，T007/T008（完整 E2E 自动化）与 G1（用户产品层）未闭环

## User Stories

### US1: 终局审计（P0）
作为主控，我要系统性地审查全项目（架构/代码/契约/安全/性能/依赖/配置/文档/测试），
找出所有"看起来有其实不能用"的假功能、隐藏前提、死代码、契约漂移、文档撒谎点。

**验收**：产出结构化审计报告（分组/严重度/文件:行号/建议），每项有明确修复预案或"有意保留"标注。

### US2: 极限压测与防穿透（P0）
作为部署者，我要知道系统在极端并发/异常输入/上游故障下的真实行为，不崩溃、数据不错乱。

**验收**：压测脚本（并发提交/限流/熔断/恢复），记录吞吐、P95、错误率、熔断恢复；极端输入（超长 prompt/畸形 JSON/注入）不 500 不串数据。

### US3: SQL 与数据正确性（P0）
作为维护者，我要审查全部 SQL：注入、锁表、死锁、N+1、慢查询、索引缺失、事务边界。

**验收**：慢查询/索引审计报告；高风险 SQL 修复；关键路径加索引；数据库备份恢复演练记录。

### US4: 契约一致性与防坑（P1）
作为调用方，我要确保前后端/API/第三方契约一致：字段名、错误码、响应结构、版本、认证头、示例可跑通。

**验收**：契约核对表（OpenAPI vs 前端类型 vs 文档示例 vs 真实响应）；不一致项修复；新增契约防坑测试。

### US5: 可观测性（P1）
作为运维，我要能看日志/指标/追踪/健康/告警，快速定位问题。

**验收**：/metrics Prometheus 指标核对；健康检查完整；结构化日志；SOP 排障手册；关键路径 trace 抽样可用。

### US6: 架构演进建议（P1，方案级）
作为架构师，我要评估 LB/Redis Cache/CDN/DB 复制/分片/消息队列/限流/熔断/健康检查在当前单机的落地方案，输出分阶段迁移路线（不强行上 Kubernetes，符合单机成本现实）。

**验收**：架构演进 ADR（每项 现状/收益/成本/风险/优先级/落地步骤）；高价值低成本项（如 Redis 缓存、CDN 静态、Rate Limit 精细）可直接落地。

### US7: 文档/SOP/ADR/目录治理（P1）
作为交接方，我要新人/运维/调用方按文档就能理解、部署、接入、排障。

**验收**：README 真实可用；部署 SOP 全覆盖（备份/回滚/重启/证书续期/代理池/压测）；ADR 记录关键决策；目录结构文档；黄金代码范例索引。

### US8: 产品增长与用户体验（P2）
作为产品负责人，我要在匿名/公益不破现有模式前提下，找增长/留存/付费场景突破口。

**验收**：结构化产品分析（定位/用户/边界/增长杠杆）；高价值低侵入项（如会话记录、限次气泡、导出）进入 backlog；不引入登录/支付（除非用户明确授权）。

### US9: 验证记录防重跑（P0 机制）
作为主控，我要验证记录可被后续优先读取，避免重复跑同一测试/优化。

**验收**：docs/verification-log.md 结构化（日期/范围/结果/备注）；workflow_status.md 反映当前终局审计状态；"验证过勿重跑"结论持续追加。

## Non-Functional Requirements

- **生产安全**：所有改动可回滚（git 主题 commit）；不破坏既有 E2E 全链路
- **真实性**：每项验收附真实命令输出/证据，禁止"跑过=完成"
- **成本现实**：单机 ARM64 2C/4G 约束；不推荐重架构（K8s/Kafka 等）除非有明确收益
- **渐进**：P0（审计+压测+SQL+契约）先行；P1（可观测/架构/文档）并行；P2（产品）后置
- **多代理编排**：主控拆解子任务，子代理并行执行，节点验收后汇总

## Success Metrics

- 审计报告 ≥ 30 项（含"有意保留"标注）
- 压测：并发 20+ 提交无崩溃，熔断恢复正常；极端输入 0 数据错乱
- SQL 审计：高风险项清零；关键表有索引
- 契约：OpenAPI/前端/文档/真实响应四者一致项修复
- 文档：README/SOP/ADR/目录齐全且与真实行为一致
- 所有改动主题 commit + push + Release（如有版本变化）

## Out of Scope

- 引入付费/登录体系（除非用户明确授权）
- Kubernetes/微服务化/Kafka 等重架构（仅出方案，不实施）
- 视频新上游接入（另立 spec）
