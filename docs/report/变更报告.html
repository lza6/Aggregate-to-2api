1. 上下文 · 这是什么项目，为什么改

听风AI 是一个把 5 家上游 AI 图像/聊天生成站聚合成统一 OpenAI 风格 /v1/* 接口的高并发公益网关。已部署生产（腾讯云东京单机 docker-compose），被真实用户调用。

核心痛点：上游生成 6-30s 慢、号池需人工、token 求解慢、单机易被脚本薅、公益服务缺合规、代码超长维护难。

本轮目标：把《下一步改进指南.md》22 条规划逐条真实落地，而非"看起来完成了"。用户明确：禁止空话/伪实现，要一次调用就通、前后端真正衔接、文档真实同步。

2. 直觉 · 为什么用这些方案

主线判断：瓶颈在上游求解器和上游生成速度，不在本服务框架/DB 层。所以拒绝"换 Postgres / 上 MQ / 分库分表"这类负优化，集中火力在：可观测、防滥用、数据安全、代码整洁、降本增效的免费层方案。

  • aiosqlite 迁移（P2-3）——同步 sqlite3 混入 async 链路会阻塞事件循环，是真 P1。to_thread 是缓解不是根治。
  • per-IP 分片锁——全局 threading.Lock 每请求持锁，高 RPS 串行瓶颈；分片锁让不同 IP 并行。
  • 日志脱敏 + httpx propagate=False——根因不是"没脱敏"，是 httpx 客户端 logger 记完整 URL 含 query 泄露 Key。
  • tail-based OTel 采样——错误 100% 采样定位问题时永不漏，正常 10% 控成本。
  • 不抽硬编码 config——nanobanana Action ID / tryingopen 目录已是"动态嗅探+静态兜底"自愈设计，抽 config 反而破坏自愈。
  • 拆文件而非重构——保持 import 向后兼容，绝不破坏调用方。

6. 验收测验 · 通过以下 10 题即理解本次变更

Q1. 为什么拒绝"换 Postgres / 上 MQ / 分库分表"？

查看答案
瓶颈在上游求解器与上游生成速度（6-30s/张），本服务框架/DB 层每秒写 <10，远未到瓶颈。当前单机 SQLite/队列方案在触发器出现前都是负优化（见 architecture-evolution.md）。

Q2. P3-6 日志泄露的真正根因是什么？修复做了什么？

查看答案
不是"没脱敏 Key 字符串"，而是 httpx 和 uvicorn.access logger 会记录完整请求 URL（含 ?api_key= query），经 root logger 冒泡进 log_buffer。修复：logging.getLogger("httpx").propagate=False + uvicorn.access.propagate=False，访问日志改由 context.py 中间件只记 path。

Q3. P2-3 aiosqlite 迁移想解决什么？为什么 to_thread 不够？

查看答案
同步 sqlite3 混入 async 链路会阻塞事件循环（真 P1）。to_thread 只是把阻塞丢线程池缓解，线程池容量有限 + 上下文切换开销。aiosqlite 让 DB I/O 真正非阻塞。

Q4. per-IP 分片锁解决了什么？为什么能保证同 IP 仍串行？

查看答案
全局 threading.Lock 每请求持锁是高 RPS 串行瓶颈。分片锁（_ip_locks[ip]）让不同 IP 并行检查，同 IP 拿到同一把锁仍串行（同 IP 本就应串行限流）。

Q5. email_pool 拆分后 from api.email_pool import LinshiMailSource 还能用吗？怎么做到的？

查看答案
能。email_pool.py 顶部 from .email_sources import (...) 转发 + noqa F401，旧 import 路径零改动。9 源拆 api/email_sources/ 子包，email_pool 从 1315 → 386 行。

Q6. OTel 自定义 sampler 的 should_sample 签名坑是什么？

查看答案
新版 OTel SDK 第 4 位参数是 kind(SpanKind)，旧版是 attributes。签名错位会让 attributes 拿到 SpanKind 对象，调用 .get() 抛 TypeError 破坏 instrumentation。需兼容双签名 + isinstance(attributes, dict) 守卫。

Q7. 版本号全链对齐具体是哪 6 处？漏一处会怎样？

查看答案
pyproject.toml / api/main.py / frontend+landing package.json / deploy/docker-compose.yml（注释 + cfsolver 镜像 tag）。漏一处 CI frontend-version-gate 校验 package.json ≠ app.version 直接卡死（实测踩过 2 次）。

Q8. conftest 加 os._exit(exitstatus) 是修复什么？为什么必须传 exitstatus？

查看答案
Windows 本地 pytest session teardown 阶段 aiosqlite 连接 join 永不返回，结果全绿但进程挂起、真实退出码被吞。第二版修复传 exitstatus（非 0），否则 os._exit(0) 会把失败测试强改为成功，掩盖回归。

Q9. 为什么 nanobanana 硬编码 Action ID 不抽 config？

查看答案
它已是 ActionSniffer 动态嗅探 + STATIC_ACTION_IDS 静态兜底的自愈设计，站点改版自动嗅探更新。抽 config 会让运维误改静态值而绕过嗅探自愈，破坏 ISSUE-03 设计。

Q10. 《下一步改进指南》22 条现状？哪 2 条未落地为什么？

查看答案
20 条 ✅ 闭环（真实代码+证据），2 条 ⬜：P0-1 cf_solver 并发提升（生产 L3 灰度需观察 camoufox 内存）与 P3-1 自建邮箱（v8.0 评估，需独立部署+域名+CF 额度）。二者均属需生产授权的风险项，已产出评估文档。
