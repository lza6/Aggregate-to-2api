## 0. 使用方法（先读我）

1. **本文件是「路线图 + 验收门禁」，不是逐行改码清单。** 每项优化标注 `[涉及文件]`、`[验证方式]`、`[风险级别]`、`[是否需用户授权]`。
2. **执行顺序**：`P0` → `P1` → `P2` → `P3`（阻塞项优先，避免「前面改 bug 后面加功能又出 bug」）。
3. 每完成一条，在对应行打 `✅` 并填 `[验证证据]`（实际运行的命令 + 真实输出摘要）。
4. **凡涉及改码的执行者**，改完必须运行：单测门禁 + ruff + 前端 build + 相关集成测试，未跑通禁止声称完成。
5. **凡涉及 UI 优化**，需要在浏览器真实点一遍（点击反馈、空态、错误态、loading 态、移动端断点）。
6. **凡涉及生产/部署/不可逆操作**（DB 迁移、CORS 收紧、CSP 开启、mem_limit 调整、cf_solver 并发调整、发版部署），必须先做影响分析 + 回滚方案，**达审批点暂停等用户确认**，不自动执行。
7. **版本回写**：每迭代一个大版本，在「第 9 节版本回写区」追加一行，写清「版本号 / 已落地条目 / 遗留风险」。
8. **旧产物清理**：每完成一个版本，按「第 8 节旧产物清理清单」清理上一版的残留垃圾代码/产物，保持都是最新顶尖版本。

> ⚠️ **本文件只做规划与验收，不含逐行代码。** 具体实现由你（或主程）在各步骤的 `[涉及文件]` 里按既有风格落地。**禁止盲目重构、禁止重复造轮子——先查项目是否已有实现再改造。**

## 3. P0 阻塞项（必须最先处理，不改直接卡后续）

### P0-1 cf_solver 单槽串行瓶颈（吞吐天花板）🔴
- **现象**：`deploy/cf_solver/config.json` 当前 `thread: 2, page_count: 1` → `max_task_num = 2×1 = 2` 并发（`api_server.py:68`）。单实例吞吐 ≈ 2/4.78 ≈ 0.42 token/s，并发上限受单槽压制。
- **根因**：`page_count=1` 意味着每 thread 只有 1 个浏览器 page 槽，求解串行化。compose cfsolver `mem_limit: 1024m, cpus: 2`（`docker-compose.yml:19,21`）资源够撑 3-4 槽但未用满。
- **[涉及文件]**：`deploy/cf_solver/config.json`（`page_count: 1` → `3`）、`deploy/docker-compose.yml:19,21`（mem/cpus 按需上调）、`deploy/cf_solver/api_server.py:47-68,149-159`（page_pool 构建）。
- **[建议]**：
  1. **第一步（最小改动）**：`config.json` `page_count: 1 → 3`，`max_task_num` 自动变 2×3=6，吞吐理论 3 倍。先本地/灰度验证 camoufox 多 page 稳定性（内存是否泄漏、page_pool 是否死锁）。
  2. **第二步（若稳定）**：compose cfsolver `mem_limit: 1024m → 1536m`、`cpus: 2 → 3`，撑住多槽内存。
  3. **第三步（横向扩展）**：复制 cfsolver2/cfsolver3 service，`IF_CF_SOLVER_URLS` 逗号列多节点，`solver_guard` 已有加权最少在途调度+failover。
- **[验证方式]**：本地 `cd deploy && docker compose up -d cfsolver`，`curl http://localhost:8001/turnstile?url=x&sitekey=x` 连打 10 次测 P50/P95；线上 SSH 采 `/v1/healthz` 的 `solve_avg_seconds`；压测 `scripts/loadtest.py` 看 RPS 上限。
- **[风险级别]**：L3（生产求解器，影响出图时延；camoufox 多 page 可能内存泄漏，需观察 `cleanup_interval_minutes` 周期重启是否仍生效）。
- **[需用户授权]**：✅ 是（生产 cf_solver 配置变更，需先灰度+回滚方案）。
- **[状态]**：⬜ 未执行（L3 生产灰度项；多节点联邦 solver_guard 已支持只差加节点，详见 `docs/architecture-evolution.md`）

### P1-3 LRU 缓存分级（热数据 TTL 分层）🟡
- **现象**：`api/cache.py` LRUCache 全量一个 `ttl`（默认 5s）。画廊缓存 + 模型列表 + 提供商状态共用同一 TTL，冷热不分，长 TTL 数据被短 TTL 拖累、短 TTL 数据被长 TTL 过期滞后。
- **[建议]**：`LRUCache` 支持 per-key TTL 或 per-adapter TTL（`set(key, value, ttl=None)` 缺省用全局）；前台展示数据 5s，模型列表 30s，提供商状态 60s。
- **[涉及文件]**：`api/cache.py`、`api/meta.py`/`api/health.py`（调用处传 per-key TTL）。
- **[验证方式]**：`tests/test_cache_persist.py` 扩展 per-key TTL 用例；浏览器观察模型列表不再每次刷新都打后端。

- **[需用户授权]**：❌ 否。
