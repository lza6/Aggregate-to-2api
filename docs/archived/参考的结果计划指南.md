# 二、主项目现状总结

## 2.1 当前架构特点

- **网关层**：5 上游聚合 + OpenAI 兼容 /v1 + MAB-EWMA 路由（成功/log10时延×负载）+ 熔断 + 预算门禁（成本门禁三态 off/observe/enforce）。
- **资源自动化**：号池（>1000 行，FSM 自愈）+ 邮箱池（7 源）+ 代理池（住宅+免费双源）。
- **反爬/求解**：cf_solver（Turnstile 求解）+ SolverGuard 联邦熔断 + captcha 统一 solved 协议。
- **agent 化**（v9~v15 沉淀）：意图识别（规则→embedding→LLM 三路）、DAG 编排（条件分支/RAG/多模态/记忆/工具/人机审批/断点续跑）、critic 自反思、记忆 L0-L3 巩固+supersede、MCP JSON-RPC 服务端（五工具）、skills 技能库（ecommerce/ppt/image_quality/prompt_refine/critic）。
- **前端**：React19 15 页管理面板 + Vue3 落地页 + Tauri2 桌面 sidecar。
- **工程**：测试五档门禁（unit/integration/chaos/performance/E2E）、CI（单测+集成+ruff+版本契约）、配置工厂（get_settings/reset_settings）。

## 2.2 当前优点

1. **真实闭环文化**：verification-log 全量证据链、Mock 不冒充真实集成、未跑通不算完成。
2. **agent 栈完整度**：从意图→规划→执行→反思→记忆→审批→续跑的全链路已闭环（国内同类少见）。
3. **安全护栏到位**：破坏性命令硬门禁 + 预算 402 + 管理 Key 独立 + request_guard 多层限流。
4. **工程规范高**：版本一致性门禁（核心 8 处）+ 20 项契约测试 + 跨文件顺序污染根治。
5. **性能意识**：MAB 路由、熔断、SSE 断线补偿（Last-Event-ID）、SQLite WAL 批量写。

## 2.3 当前主要问题

| 类别 | 问题 | 证据/影响 |
|---|---|---|
| **agent 用户体验** | 黑匣子现象：Agent 页只有 SVG DAG 图+轨迹面板，无「为什么这么规划/每节点在做什么学什么」的教学化引导 & 节点大白话解释 | `frontend/src/pages/Agent.tsx`、`DagGraph.tsx` 现状 |

| **扩展场景受限** | 视频能力已由 falai 承载（txt2vid/img2vid minimax-h3-max，见 `api/providers/falai.py`），但仅单一供应商、无编排/SDAG 集成；PPT/电商主图全流程缺（用户明确提到电商/PPT/视频需求） | `api/providers/falai.py`（CAP_TXT2VID/CAP_IMG2VID）、`api/skills/ppt` 为单技能级 |

## 2.4 风险点

1. **agent 能力与服务核心脱节**：用户在场的使用路径是「生成图片/对话」，agent 是增强；若 agent 不「教学化/小白化」则价值被埋没。
2. **过度追求 agent 能力而轻视体验**：已有 24 个 agent 开关、DAG 八类节点，但小白用户可能根本不会用。
3. **扩展场景若真做**：付费上游预算红线（Mock 验证铁律）会限制真实效果验证。

## 2.5 技术债（按严重度）

# 四、差距分析

## 4.1 功能层

- **agent 教学化/小白易用**：主项目缺（参考 CowAgent 可视化 + learn-agent 渐进教学）。★
- **用户 skills 沉淀闭环**：主项目缺（参考 SkillClaw 自动沉淀 + 审批）。★
- **扩展场景**：主项目视频能力已由 falai 承载（`CAP_TXT2VID/CAP_IMG2VID`），缺的是多供应商抽象统一 + 编排集成 + PPT/电商主图全流程（参考 Pixelle/ppt-master/commerce-agents）。★

## 4.2 架构层

- **网关多模态化**：主项目是「图像网关」，参考项目（freellmapi/OmniRoute）已是「多模态/多渠道网关」；主项目可扩展 provider 抽象承接视频/音频。
- **MCP 外部接入**：主项目 MCP 是内部五工具，参考 smart-mcp-proxy 的渐进暴露 + Streamable HTTP 接入外部 client。★

## 4.3 工程层

- **技能工程化**：主项目 5 技能无 schema/validate/expected_results，参考 100x-tiktok 四件套 + SkillSpector 扫描。★
- **配置/模块拆分**：`config/__init__.py` 821 行 + `api/agent` 2802 行未拆（参考 1000 行内拆分模式）。

## 4.4 性能层

- **上下文/token 成本**：主项目无上下文压缩，参考 headroom/context-mode/rtk-master（token 削减 60-90%）。
- **记忆检索单一**：主项目 memory.py query() 为纯 SQL 排序（importance/last_accessed_at），无向量/全文检索（差距比"向量单检索"更大），参考 mem0 三流融合。

## 4.5 安全层

- **技能开放风险**：若开放用户 skills，主项目缺 SkillSpector 式输入扫描 → 必须前置。

# 六、优先级优化路线图（P0/P1/P2）

> 设计原则：先补体验与安全（小白能用、技能可控）→ 再扩场景（视频/PPT/电商）→ 后深化效率（token/记忆/网关）。全部改造遵循「真实落地、不动大地基、可回滚」铁律。

## P0 必须先做（影响核心体验/安全边界）

### P0-1 用户技能自动沉淀闭环（参考 SkillClaw/SkillOpt）
- **做什么**：会话产物→LLM 摘要候选技能（主项目 frontmatter 格式）→历史 DAG 重放验证（复用意图评测；**GATE 通过判据：候选技能在 held-out 任务集上不降低既有技能效果即可 adopt，阈值由 admin 面板可配 `IF_SKILL_GATE_THRESHOLD`，缺省 0.8**）→预算门控→admin 审批→写入 `api/skills/`。
- **为什么**：用户明确要求「沉淀训练用户自己的 skills」，这是产品差异化核心。
- **改哪些**：`api/agent/`（新 `skill_sediment.py`）、`api/routes/agent_*.py`、`frontend/src/pages/Agent.tsx`、`frontend/src/components/`.
- **前置依赖**：P0-2 技能安全扫描（B1 先于 B2，安全前置）。
- **预期收益**：每个可用 DAG 任务 → 一个可复用 skill。
- **风险**：中（新增核心功能）。**数据迁移**：无（新表 `skills` + `skill_versions`）。**兼容性**：不破坏现有 5 预设技能。
- **验证**：`tests/test_skill_sediment.py`（Mock LLM 重放）+ 前端 vitest。**回滚**：`IF_SKILL_SEDIMENT_ENABLED=0`。

### P0-2 开放用户技能的安全前置（参考 SkillSpector）
- **做什么**：`scripts/skillspector.py` 静态扫描（prompt 注入/数据外泄/提权/供应链）+ 0-100 风险分 + baseline 抑制 + admin 报告。
- **为什么**：开放技能 = 引入第三方法；无扫描即放大供应链投毒风险。
- **改哪些**：`scripts/skillspector.py`、`api/routes/agent_*.py`（skill 上传校验）、`frontend/src/pages/Agent.tsx`。
- **风险**：中。**兼容性**：仅影响新技能上传路径。

### P0-3 黑匣子打开 + 教学化引导（参考 CowAgent/learn-agent）
- **做什么**：Agent 页增加「节点级大白话解释」+「为什么这样规划」+「学习故事线」：把 DAG 节点/意图/critic 结果转为面向小白的逐步说明；开放 `?mode=learn` 教学层（每节点一屏解释）。
- **为什么**：用户明确要「让小白理解产品、使用产品时学习背后原理」。
- **改哪些**：`frontend/src/pages/Agent.tsx`、`DagGraph.tsx`（加 explain 面板）、`api/routes/agent_dag*.py`（节点 explain 字段）。
- **风险**：低-中（纯增量 UI+字段）。**回滚**：`IF_AGENT_LEARN_MODE=0`。

### P0-4 技能工程化四件套（参考 100x-skill-tiktok/benjamin-plus/anthropics 规范）
- **做什么**：主项目 5 技能升级为 `SKILL.md + schema.json + validate.py + expected_results`；`scripts/validate_skills.py` 一键门禁。
- **为什么**：技能可验证化是「真实闭环」的承载。
- **风险**：低。**兼容性**：无损（追加字段）。

## P1 高价值改造（明显提升质量/可维护/扩展力）

### P1-5 记忆双升级（参考 mem0+ai-memory）
- **做什么**：`MemoryStore.query()`（现为纯 SQL 排序，无向量/全文检索）升级三流检索（语义+BM25+实体）+ explain 分解 + apply_decay 数学化（两列）。
- **为什么**：记忆是 agent 长期价值；纯 SQL 排序差距显著；黑匣子可解释支撑教学化。
- **风险**：中。**兼容性**：SQLite 加列（可回滚）。**验证**：单测 20 例。

### P1-6 MCP 外部接入 + 渐进工具暴露（参考 smart-mcp-proxy/x64dbg）
- **做什么**：`/v1/mcp` 升级 Streamable HTTP；`retrieve_tools`（BM25）+ `describe_tool` + read/write/destructive 三意图注解 + 新工具隔离审批。
- **为什么**：让外部 client（Claude Desktop/Cursor）开箱即连。
- **风险**：中（协议变兼容）。**验证**：MCP 测试 suite。

### P1-7 桌面全生命周期深化（参考 dsh-desktop）
- **做什么**：自升级补 stable/beta 通道 + SemVer 严格化 + checkpoint 启动恢复 + safe-mode 诊断导出。
- **为什么**：桌面端从「能用」到「体面」。
- **风险**：低-中。**验证**：cargo check + 真机待验证。

### P1-8 视频扩展编排化（既有 falai 视频抽象统一 + 多供应商扩展；参考 Pixelle/zack-d）
- **做什么**：①对既有 `falai.py` 视频能力（txt2vid/img2vid）做**多供应商动作族抽象统一**（`image_to_video`/`text_to_video` 基类动作，adaptr 归一视频轮询/上传/下载，参照 zack-d `_submit_and_poll`）；②Storyboard→镜头 schema + SSE `ProgressEvent` 逐帧进度；③DAG 视频节点集成。**注意：非从零新增，falai 已承载单供应商视频**。
- **为什么**：用户明确视频需求；falai 已证可行，扩展为多供应商 + 编排层。
- **风险**：高（新增 provider 动作族 + 编排集成）。**红线**：付费上游一律 Mock 验证。**验证**：Mock + E2E（`IF_MOCK_UPSTREAM=1`）。

### P1-9 电商/PPT 技能化（参考 commerce-agents/ppt-master/feichanggege）
- **做什么**：ecommerce skill 加 provenance/fencing/checkout-staged；ppt skill 升级可编辑 PPTX+模板。
- **为什么**：电商/PPT 场景是用户显式扩展诉求。
- **风险**：低。**验证**：单测 + 前端展示。

### P1-10 求解器细节加固（参考 captcha-solver）

- **风险**：低。**验证**：solver 测试。

## RT-1 P0-1 技能自动沉淀闭环

| 项 | 反证结论 |
|---|---|
| 未验证假设 | "历史 DAG 重放验证能可靠判断候选技能好坏"——真实 DAG 任务多含随机上游结果（生图质量主观），重放分数波动可能误杀好技能 |
| 漏掉失败场景 | 用户沉淀技能的 prompt 可能含其私有业务数据 → 技能公开后泄露；技能间命名冲突/重复沉淀堆积 |
| 过度乐观点 | 假设 LLM 摘要候选技能零成本；实际每技能需 1-3 次 LLM 调用，大批量沉淀烧预算 |
| 更简单路径 | 先做「手动保存」技能（用户对自己满意的 DAG/提示词点收藏→入库），自动沉淀作为 P1 后置 |
| 最小证伪实验 | 用 5 个已知好/坏技能做「重放验证」：好技能分数必须显著高于坏技能；若区分度不足则降级为手动收藏 |
| 建议 | **先做最小实验再实施**；同时 P0-2 技能扫描必须前置（否则技能投毒风险） |

## RT-4 P1-5 记忆双升级（mem0+ai-memory）

| 项 | 反证结论 |
|---|---|
| 未验证假设 | "BM25（SQLite FTS5）与向量 RRF 融合在 SQLite 上性能可接受"——FTS5 检索热路径开销需压测 |
| 漏掉失败场景 | 加 access_count/last_accessed_at 两列后存量数据迁移；检索 explain 存储膨胀 |
