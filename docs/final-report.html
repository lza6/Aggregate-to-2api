1. 任务目标与上下文

本次审计的核心目标是 IMP-11：画廊/统计缓存持久化——缓存到期时同步写回 DB，防重启后缓存空窗期。同时覆盖全链路审计、P0/P1 安全修复、文档对齐、配置补全、DLQ 管理 API 补齐。

显式需求

  • LRU 缓存 set 时同步写入 DB cache_store 表
  • stop 时全量 flush 所有内存条目到 DB
  • start 时从 DB 恢复缓存，消除重启空窗期
  • 新图出图后自动失效画廊缓存
  • 所有改动有测试覆盖

隐式需求（审计发现）

  • P0: download_image 无 SSRF 防护 → 上游返回恶意 URL 可发起内网请求
  • P0: 画廊密码比较非恒定时间 → 时序侧信道攻击
  • P1: duration/resolution 无值域校验 → 错误参数浪费上游资源
  • P1: POST /v1/generate/async 缺少 Location 标头
  • P1: 死信队列只读，无重试/清空 API
  • P1: _validate_model 中 kind 字典访问可能触发 500
  • P1: wait_result 超时返回合成数据而非完整结构
  • P1: recover_stale_tasks 300s 门槛与 TASK_HARD_TIMEOUT 480s 不匹配
  • P2: _validate_ratio 函数体内冗余 import re
  • P2: _validate_model 中 kind 字典使用 .get() 替代 []

3. IMP-11 数据流

set(key, value) │ ├──→ 内存 OrderedDict（LRU 淘汰） │ └──→ _DbPending.upserts += (key, json_value, ttl) │ └──→ [每5轮] _flush_pending_to_db() │ └──→ DB.save_cache_batch() │ └──→ INSERT OR REPLACE INTO cache_store stop_reaper() │ └──→ _flush_all_to_db() │ └──→ 遍历 _data 所有未过期条目 → DB.save_cache_batch() start_reaper() │ └──→ restore_from_db() │ └──→ DB.load_cache_snapshot() │ └──→ 反序列化 JSON → 写入内存 _data worker._finish(status="completed", image_url=...) │ └──→ gallery_cache.invalidate_prefix("gallery:") │ └──→ 删除所有 gallery:* 前缀的内存条目 │ └──→ _DbPending.deletes += [key] → flush 时 DB.delete_cache_batch()

7. 知识测验

以下测验验证你对本次变更的理解。点击按钮查看答案。

Q1: IMP-11 缓存持久化中，LRU 淘汰的条目是否也会写入 DB？为什么？
是。在 set() 方法中，当超出 maxsize 淘汰最久未用条目时，会将淘汰项也追加到 _pending.upserts 缓冲区。这样即使重启后内存中该条目已被淘汰，DB 中仍有备份，避免重启后缓存空窗期。
Q2: 为什么 download_image 需要 SSRF 防护？
上游返回的 result["image"] URL 可能被恶意重定向到内网地址（如 http://169.254.169.254/ 云元数据服务）。如果 download=True，worker 会调用 download_image 下载该 URL，无防护时可发起 SSRF 攻击。
Q3: 画廊密码比较为什么从 password != pwd 改为 hmac.compare_digest？
字符串直接比较 (!=) 是时序非安全操作——攻击者可通过测量响应时间逐字符猜测密码。hmac.compare_digest 保证恒定时间比较，消除时序侧信道攻击。
Q4: 新增的 DLQ 管理端点有哪些？
POST /v1/dead-letter-queue/{task_id}/retry（从死信队列移除指定任务）和 DELETE /v1/dead-letter-queue（清空死信队列）。之前只有只读的 GET /v1/dead-letter-queue。
Q5: recover_stale_tasks 的 stale_after 参数从 300 秒改为多少？为什么？
改为 TASK_HARD_TIMEOUT + 60 秒（默认 480+60=540s）。原硬编码 300s 小于 TASK_HARD_TIMEOUT 480s，一个处理了 301-480s 的合法任务可能被重启误回收为孤儿任务。
