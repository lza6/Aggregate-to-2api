1. 任务背景与目标

imagefree 高并发图像生成 API（imagefree.tingfengai.art）在应对 270+ RPS 时暴露了三个系统性薄弱点，本次合并将其推进到可验证、可维护、可部署状态：

  • ISSUE-01 存储驱动可插拔：单体单进程的限流桶 / 编辑互斥锁 / Token 池全部内存实现，无法水平扩展。方案引入 StorageAdapter 抽象层，单机默认 SQLite/Memory（零外置依赖），集群可用 IF_STORAGE_BACKEND=redis 切换到 Redis 分布式锁 + 滑动窗口 Lua 限流。
  • ISSUE-02 动态 IP 风控：防刷策略曾在 request_guard.py 写死单个 IP（如一个恶意刷量 IP），缺乏规则引擎。方案新增 SQLite ip_blocklist 动态封禁表 + 内存高速缓存 + 管理面封禁/解封端点 + 频繁超限自动入黑名单。
  • ISSUE-03 Action ID 自愈：Next.js Server Action 编译哈希随上游改版变化，静态硬编码 Next-Action 必然过期导致 404。方案新增 action_sniffer.py 动态嗅探 + 失配自愈 + 后台保活。

3. 关键反向审查结论（Red Team）

  • 最脆弱假设：“仅依赖 XFF 首段即可拿真实客户端 IP”。被独立安全审查证伪——公网可直连时客户端可任意伪造 XFF，绕过封禁/限流/白名单，甚至把第三方 IP 打黑。已修复为「对端非受信代理一律以 socket 对端为准」。
  • 六个月后最可能失败点：上游 Site 再次改版使 Action ID 过期。已通过 force_refresh 失配自愈 + 后台 keepalive 缓解，且 实测上游当前三个 Action 均已过期（生成 7f904a21… vs 代码旧值 7fb61a58…），本项目上线即触发一次嗅探自愈，正是收益。
  • 被遗漏的边界：管理端点与客户端共用同一把 Key 被审查指出（B2）。已引入独立 IF_ADMIN_KEYS，未配置默认拒绝，仅 IF_ADMIN_KEY_OPEN=1 显式开放。
  • 更简路径：相对于引入完整外置 Redis 依赖，单机默认保持 SQLite/Memory 是更保守、可回滚的路径；Redis 仅为集群可选增强。
