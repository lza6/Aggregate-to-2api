1. 任务背景与目标

本周期承接四类生产级工作，目标是将 v6.6.0 推进到可验证、可部署、可维护、可审计状态：

  • P3-3 多实例横向扩展评估（只评估不实施）——确认单机 SQLite + 内存队列 + 单 worker token 串行下是否值得集群化；
  • P3-4 号池补满速率监控——新增号池「今日新增/日均新增/距目标/预计达标」与「消耗/获得积分聚合」画像；
  • P0 安全加固——消除 /v1/meta、/v1/chat/auth/status 匿名泄露完整 API Key 的漏洞；
  • 可观测性闭环——错误码聚合、告警扩充、任务全链路日志串联、Prometheus counter 语义修复。

2. 原始问题

  • Key 泄露（P0）：GET /v1/meta 与匿名 GET /v1/chat/auth/status 直接返回完整 api_key，任何匿名访问者都能拿到站长密钥。
  • 号池补满无观测（P3-4）：1 万账号目标下，站长无法知道每天补多少、何时达标、积分消耗画像。
  • 扩展决策无证据（P3-3）：「是否值得多实例横向扩」长期悬而未决，README 声称 270+ RPS 但无稳态基准支撑。
  • metrics 计数叠加（C1）：Prometheus counter 用 DB 累计绝对值直接 inc()，每次 scrape 都重复叠加计数。
  • 流式错误丢帧：聊天流式 server_error 终帧无 choices 被前端丢弃 → 用户停留「正在思考…」而非看到错误。

                                        │
                                        ▼
              [turnstile 求解 4.33~4.78s/个] ← cfsolver 单槽串行 ←── 瓶颈点(不可多实例分摊)

关键结论：入口/入队/SQLite 写均非瓶颈（消费天花板 ≈81 req/s vs 线上峰值 0.12），真正瓶颈是 cfsolver 单槽串行求解。横向加实例只增加 API 空载，不增加出图吞吐。

6. 关键设计决策

  • 增量 counter 而非绝对值：_counter_inc_absolute() 记录上次已曝光绝对值，只 inc 差值——符合 Prometheus counter 单调语义，DB 清理回落不产生负值。
  • 管理 Key 继承设计：IF_ADMIN_KEYS 为空时回退继承 IF_API_KEYS（auth.py:49）——运维零配置可用，但语义上是「业务 Key 即管理 Key」的降级模式。
  • growth/cost 按 provider 过滤：两个画像都以 nanobanana 为口径，与号池主路径一致。
  • task_logs 严格 UUID 门禁：uuid.UUID(task_id) 校验防任意子串误伤其他任务日志。

9. 兼容性、迁移与回滚

  • DB 迁移：account_pool 新增 credits_used_total/images_used/last_used_at 与 chat_usage.cost_usd 均为幂等 ALTER（自动迁移），旧数据兼容（NULL→0）。
  • API 兼容：auth/status 响应移除完整 key（匿名场景）是破坏性变更——任何依赖匿名取完整 Key 的调用方会拿到空串；站长需携带管理 Key 访问。已在前端同步（复制按钮仅站长可见）。
  • 回滚：imagefree-api:6.5.1 镜像仍在，compose 改回 tag + up -d --force-recreate 即可。

10. 已知限制与剩余风险

⚠️ 安全边界（需用户决策）：线上未配置 IF_ADMIN_KEYS，仅 IF_API_KEYS。按 auth.py 继承设计，此时任何持有业务 Key 者即可通过 /v1/chat/auth/status 取回完整 Key（已线上实测确认）。这不是代码缺陷（继承是有意设计），而是配置级安全边界——生产应配置独立 IF_ADMIN_KEYS 管理池以真正隔离「业务 Key」与「站长管理 Key」。建议后续加固。
  • 号池达标极低：ok=4/10000，日均新增 ≈12（REGISTER_COOLDOWN=90s 上限）——补号能力上限非缺陷，可调 IF_REGISTER_COOLDOWN 提速。
  • 扩展评估仅本机基准：多实例可行性仅给出实验路径，未实际起 2 实例验证（符合「只评估不实施」授权）。
  • 全量测试套件：部分集成/混沌用例依赖 8001 mock solver 与网络，单进程全量运行曾出现挂起，本轮以「逐文件独立进程」验证替代，未覆盖全部混沌用例。

11. 使用者须知

  • 站长取完整 Key：携带管理 Key 调 GET /v1/chat/auth/status（Authorization: Bearer <key>）。
  • 生产加固：配置 IF_ADMIN_KEYS 独立管理池；/v1/chat/auth/status 建议配 IP 白名单最小暴露。
  • 排障：GET /v1/tasks/{task_id}/logs 一个任务 ID 看全链路（内存日志+慢日志+SSE 事件+DB 终态）。
  • 观测：/metrics 现为 counter 增量语义，可用 Prometheus 正常 rate()。
