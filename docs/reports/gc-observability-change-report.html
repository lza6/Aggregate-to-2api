背景与目标

项目的 api/base64_store.py 已有完整清理逻辑——按 mtime 判定过期的 clean_expired 与按最旧优先的配额保护 enforce_quota，且 test_img_gc.py 已有覆盖。但这些资源的水位完全不可见：运营者看不到缓存目录有多大、多久会被后台定时任务清掉、配额是否接近上限。本次交付为这一闭环补上最后一环——可观测。

目标不是新增清理能力（已有），而是把一个静默的后台过程变成管理面板上一目了然的数字。

核心交付物： GET /v1/stats 新增 base64_gc 段，字段包括 total_files / total_gb / hot_files / hot_gb / cold_files / cold_gb / quota_gb / usage_pct / pending_cleanup_count / pending_cleanup_gb。

架构与数据流

热冷拆分沿用系统既有的 mtime 语义，与后台清理保持逐字一致，不引入第二套判定规则：

base64 文件写入（save_base64）
   │  mtime = 写入时刻
   ▼
gc_stats() 一次目录扫描
   │  对每个文件: now − mtime > IF_BASE64_FILE_TTL ?
   ├──── 否 ────► hot（未过期）
   └──── 是 ────► cold（待清理）
   ▼
/v1/stats 实时计算（不经过 10s LRU 缓存）
   └────► Dashboard「base64 缓存」「待清理」卡片

关键设计点：pending_cleanup_count 与下一次 clean_expired 实际会删除的文件数精确一致——两者使用同一判定式「now − mtime > ttl」，因此「待清理」是一个有真实含义的数字，而非估算。

关键设计决策

  • 热冷判定沿用 mtime 而非引入 atime/访问计数——与 clean_expired 完全一致，避免「统计口径」与「清理口径」分裂。
  • 实时计算而非缓存——base64_gc 直接调用 gc_stats()，不经过被 LRU（TTL 10s）缓存的 overview，保证水位数字始终新鲜。
  • 纯增量、无 schema 迁移——不新增配置、不改数据库、不依赖任何外部服务，风险面最小。
  • 防御式渲染——前端对 base64_gc 缺失（旧后端）显示 -，不崩溃。

变更测验 / Quiz

提交前不会显示答案。通过分数线：80%。

Q1　gc_stats() 中「cold」文件的判定条件是什么？

解析：cold 与 clean_expired 使用同一判定式，因此「待清理数」= 下次清理实际会删的数量。

Q2　base64_gc 段的数据是否经过 10 秒 LRU 缓存？

解析：gallery_cache 只缓存 overview / daily / monthly；base64_gc 实时计算，保证水位新鲜。

Q3　目录存在但无读权限时，gc_stats() 的行为？

解析：os.listdir 已纳入 try/except，权限/瞬时失败按空目录处理，这是独立审查 V1 的加固点。

Q4　usage_pct 的分母（配额）来自哪个配置？

解析：IF_IMG_MAX_GB 默认 5.0 GB，超限时按最旧优先清理至 80%，即配额保护的同一配置。

Q5　本次改动是否引入了数据库迁移或新配置项？

解析：可观测闭环只读已有目录，不落库、不加配置，风险面最小。

Q6　前端 Stats.base64_gc 的类型声明是？

解析：独立审查 S1 后改为可选，与 Dashboard 的防御式渲染一致。

Q7　哪个验证证明了「待清理数」与真实清理语义一致？

解析：单测 test_gc_stats_hot_cold_split + clean_expired 同式判定，E2E 只做存在性检查。

Q8　本次交付在 Git 上的最终形态是？

解析：遵循约束只在 main 分支操作，维护单一主干。

Q9　线上部署目前的状态是？
