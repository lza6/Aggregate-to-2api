# P3-3 多实例横向扩展可行性评估（只评估，不实施）

> 结论链路：**不值得横向扩**。当前单机未饱和，真正的吞吐瓶颈是「生成通道」（turnstile 求解串行 + 上游限流），而非 API 入队能力。
> 数据口径：线上真实探针（腾讯云东京 `43.165.173.36`）＋ 本机可复现基准实验。

---

## 1. 结论速览

| 问题 | 判定 | 依据 |
|------|------|------|
| 单实例是否饱和 | **否** | 线上 CPU 5%、内存 113MiB/256MiB、队列深度恒 0 |
| 入口入队是否是瓶颈 | **否** | 本机严格基准：可持续 0-429 入口吞吐 **≈150 req/s**（P95=0.335ms）；消费/完成天花板 **≈81.41 req/s**（P95=0.987ms） |
| 真正的吞吐瓶颈 | **生成通道** | cfsolver 单槽串行求解，每 token 均 4.78s → 单实例仅 ~0.84 img/s |
| 是否值得横向扩 | **不值得** | 线上峰值 ~0.12 req/s，比 API 消费天花板（81.41 req/s）低 ~679 倍裕量 |
| 切 Redis + 持久化队列是否值得 | **当前不值得** | 仅为「多实例共享队列」所需；多实例不解决生成通道瓶颈，徒增依赖与改造面 |

**推荐：明确不做集群化。** 若未来真实出图量逼近单实例生成通道上限（≈0.84 img/s ≈ 每天 7.3 万张），应先突破「生成通道并发」（多 token 并行 / 多 key / 多出口 / 降单张求解耗时），而非扩容 API 层。

|------|------|------|------|
| imagefree-api | 5.01% | 113.7MiB | 256MiB |

- API 资源占用极低（CPU 5%、内存 44%），**远未触达单机上限**。
- cfsolver 占 923MiB（接近其 1GiB 上限）——求解器才是重资源，且是单点。

### 2.3 近 7 天请求峰值（按小时，读 `imagefree.db`）

```

常规峰段：300~400 请求/小时 ≈ 0.08~0.11 req/s
```

## 3. 本机最小基准实验（可复现证据）

脚本：`%TEMP%\imagefree_bench\bench_engine.py`（不入仓库，见 §6 复现步骤）
方法：patch `engine._process` 为纯内存快路径（`db.get → mark_started → mark_finished`），**零真实上游 / 零 turnstile 求解 / 零 token 池 / 零生产库污染**，全新临时 SQLite。**不调用 `engine.start()`**（避免 token 池 prefetch 触发真实求解），手动构造 worker 池并置 `engine._started=True`，每档独立 Engine + 独立临时 SQLite。

配置对齐线上：`worker=4`、DB 写池=3、DB 批量写开（window=0.2s）。

实验分两个口径，比单点更可信：
- **口径 A（精确速率持续发射）**：用漂移纠偏平行 pace 协程按目标速率发射，找「队列平稳、被接受全 drain、0 429」的可持续入口吞吐。
- **口径 B（队列饱和）**：持续灌入让队列保持饱和，找「消费/完成」天花板。

### 口径 A · 可持续 0-429 入口吞吐

| 目标RPS | 命中 | QueueFull | 接受率 | 实测RPS | 完成 | 剩余队列 | P50(ms) | P95(ms) |
|---|---|---|---|---|---|---|---|---|
| 40 | 121 | 0 | 1.0 | 39.76 | 121 | 0 | 0.255 | 0.376 |
| 100 | 302 | 0 | 1.0 | 100.52 | 302 | 0 | 0.139 | 0.297 |
| 150 | 453 | 0 | 1.0 | 150.22 | 452 | 0 | 0.124 | 0.335 |
| 400 | 1208 | 0 | 1.0 | 400.65 | 461 | 743 | 0.091 | 0.284 |

- **可持续入口吞吐 ≈ 150 req/s**（命中453、完成452、剩余队列0、P50=0.124ms / P95=0.335ms）——队列平稳、全部完成、零 429。
- 400 req/s 只是瞬时可接纳（接受率1.0 但队列增长至743，非稳态）。

### 口径 B · 消费/完成天花板

| 接受 | QueueFull | 消费RPS | 完成 | P95(ms) |
|---|---|---|---|---|
| 400 | 0 | **81.41** | 244 | 0.987 |

- → 消费/完成天花板 ≈ **81.41 req/s**（244 个任务在 ~3s 内完成）。

**关键对比：**
- API 通用层日常可持续入口 ≈ **150 req/s**（P95=0.335ms）；消费天花板 ≈ **81.41 req/s**（P95=0.987ms）。
- 线上真实出图：4 worker / 4.78s ≈ **0.84 img/s**（瓶颈在 turnstile 单槽串行）。
- 消费天花板 81.41 = 线上真实出图速率 0.84 的 **≈ 96.9 倍**；线上峰值 0.12 req/s，比消费天花板低 **≈ 679 倍裕量**。

> 注：早期实验用「并发 10 档」得出过一个表面更高的峰值（749.59 RPS），但该档实际 429 接受率仅 0.859（91% 请求被丢弃），反映的是瞬时入队而非稳态能力，不可作为「API 扛得住」的结论。本版用口径 A/B 校准后的 150/81.41 为准。

## 4. 瓶颈判定与成本收益分析

### 4.1 三大瓶颈点逐一确认

| 瓶颈点 | 现状 | 是否是多实例可解 |
|--------|------|------------------|
| ① 单 worker token 串行 | 每条任务先等 `solve_turnstile`（4.78s），cfsolver 单槽串行 | ⚠️ 多实例**不解决**——cfsolver 是单点，跨实例仍共享同一求解器 |
| ② SQLite 单写 | 入口入队是唯一写热路径（INSERT pending），已有连接池+批量写窗口 | ❌ 不解决——实测消费天花板 81.41 req/s 证明 SQLite 写不是瓶颈 |
| ③ 内存队列跨实例不可见 | `CountedPriorityQueue` 为进程内 asyncio 队列，多实例无共享 | ✅ 唯一需要 Redis 的理由（持久化队列） |

### 4.2 切换 Redis + 持久化队列的成本收益

| 维度 | 判断 |
|------|------|
| 代码就绪度 | `IF_STORAGE_BACKEND=redis`（`storage/redis_adapter.py`）、`IF_PERSISTENT_QUEUE_ENABLED=1`（`db/queue_store.py`）**均已实现** |
| 环境现状 | **redis python 包未安装**、无 Redis 服务、生产未启用 |
| 收益 | 仅当多实例共享持久队列时才体现。当前流量远未触发 |
| 成本 | 引入外部依赖 + 运维；且**跨实例 SSE 事件流、token_pool 池、号池/注册单例、画廊缓存、限流位（memory）全都要改造**，链路长、风险高 |
| 结论 | **当前零收益**。若要扩，应先确认「生成通道是否需要多实例分摊」——而 cfsolver 单点决定了多实例扩不出求解吞吐 |

## 5. 最小实验方案（若坚持验证多实例可行性）

不实施；仅给出前端验证路径，供后续决策：

1. **生成通道探针（首要）**：确认是否值得多实例 —— 起 2 个 API 实例共享同一 cfsolver，测出图速率是否仍被 `solve_avg=4.78s` 恒定压住。若出图速率不随实例数线性增长，则**加实例只增加 API 空载，不增加出图吞吐**，结论即「不做」。
2. **多实例一致性（可选）**：若决定走 Redis —— 起 2 个 API 实例，`IF_STORAGE_BACKEND=redis` + `IF_PERSISTENT_QUEUE_ENABLED=1`，验证：任务不双重消费（持久队列排他消费）、SSE 事件跨实例可达、token 池不重复求解。
3. **复用现有基准**：`%TEMP%\imagefree_bench\bench_engine.py` 可加 `--servers` 起多实例验证。

## 7. 结论

- **单实例未饱和**：CPU 5%、内存 44%、队列恒 0。API 通用层消费/完成天花板 ≈ **81.41 req/s**（P95=0.987ms），日常可持续入口 ≈ **150 req/s**（P95=0.335ms），vs 线上峰值 0.12 req/s（**679 倍裕量**）。
- **瓶颈在生成通道**：turnstile 求解串行（4.78s/个）+ 上游限流。多实例扩的是 API 空载，**不增加出图吞吐**（cfsolver 单点）。
- **启动条件（才需要重新评估）**：当真实出图率逼近 ~0.84 img/s（≈ 每天 7.3 万张）时，才应考虑突破生成通道并发，而非扩容 API 层。
- **当前动作**：不实施集群化、不切换 Redis/持久化队列。保留已就绪的代码（`IF_PERSISTENT_QUEUE_ENABLED`）作为未来选项。
